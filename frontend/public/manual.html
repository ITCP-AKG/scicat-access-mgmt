SciCat Access Management — User Manual

The source of truth for access groups, membership, resource grants, expirations and ownership transfer across your SciCat instance.

Legend for who may perform an action: admin SciCat administrators   group manager a user listed as a manager of that group   any user any signed-in user (read-only)

1. What this app does

SciCat can store an access group on a user or a dataset, but it has no place to manage those groups — to say who belongs to a group, for how long, or what happens when someone leaves. This application fills that gap. It is the source of truth; it computes each person's effective access and writes it back into SciCat automatically.

You do this here……and the app does this to SciCat
Add Alice to group catalysis-teamWrites catalysis-team into Alice's UserIdentity.profile.accessGroups
Apply group proposal-42 to 30 datasetsAdds it to each dataset's accessGroups (or sets ownerGroup)
Give a postdoc access until 31 DecActivates and then automatically revokes access on that date
Deactivate a departing userEnds their memberships, hands what they personally own to a successor, and logs every change

2. Signing in

Authentication is handled by SciCat, so you use the same account as for SciCat and catorga.

  1. Already signed in to catorga in this browser (including via SSO)? The app picks up that session automatically.
  2. University (KIT) users who are not signed in yet: sign in to catorga in this browser, then come back (or reload). The sign-in form here is only for SciCat functional accounts such as admin.
  3. Your name appears top-right, with (admin) or (manager of N).
New users People become visible here after their first SciCat/catorga login, which creates their SciCat identity — there is no separate account to create. What you can do depends on your role (next section).
Sessions Your session uses your SciCat token. Use Sign out (top-right) on shared machines; it also stops this app from re-using the current catorga session (a new catorga sign-in is picked up again). When the token expires you are returned to the sign-in screen. "Service unavailable" errors mean SciCat itself is down — your session is kept.

3. Roles & permissions

RoleCan do
adminEverything: create/delete/retire groups and set their managers, manage any membership, apply/remove any grant (including owner grants), run projection & reconcile, define transfer rules, deactivate users, and view the audit log.
group managerFor the groups they manage: edit the description, add/remove members and change their dates, and grant access to resources that one of their own groups owns. Managers also see the Users, Resource Grants and Expiry pages.
any userSee the list of groups. (Members, users and history are visible to managers and admins only.)
Why an action is greyed out or returns 403 Buttons that change data only appear for admins (and managers, where relevant). If you believe you should have access to a group, ask an admin to add you to that group's Managers list.

4. Groups

Open Groups from the left nav. This is the registry of every managed access group. Each group's name is the exact string written into SciCat.

Create a group admin

  1. Click New group.
  2. Enter a Name (e.g. catalysis-team-alpha), pick a Category, add an optional Description.
  3. Click Create. The group appears in the list.
Example

A new research group joins the lab. Create research-group category group schmidt-lab, description "Prof. Schmidt's surface catalysis group". You can now add members (§5) and grant it access to resources (§7).

Reserved & duplicate names are rejected Names that collide with SciCat's special groups (admin, globalaccess, all, ingestor, archivemanager, …), with an existing group, or with a per-user group are refused with an explanatory error. Names may contain letters, digits and . _ : @ + - (no spaces, max 64). Group names are case-sensitive in SciCat: ROCK-IT and rock-it are different groups.
Name already used in SciCat? If some users already carry the name in SciCat (e.g. a lab group assigned before this app), the dialog says how many and asks you to either add them as members or remove it from them — once the group is managed here, only its members keep it.

Edit, retire or delete a group admin group manager

Click a group row to open its detail page and use Edit. Managers can change the description; admins also the category, the managers and the status. Retiring a group removes its access from everyone (memberships and grants are kept, so re-activating restores it).

Delete is guarded admin The delete dialog shows how many members, grants and transfer rules still use the group. To delete anyway, tick the cascade option: memberships are ended, grants are withdrawn from the SciCat resources, and referencing rules are removed. Either way the name is removed from every user's SciCat groups.

5. Membership

Membership is who belongs to a group. Manage it from a group's detail page (Members panel), and review it per-person from the Users page.

Add a member admin group manager

  1. Open the group → Add member.
  2. Search the directory in the user picker and select the person.
  3. (Optional) set a time window — see below. Leave blank for indefinite access.
  4. Click Add. The change is projected to SciCat immediately.

Time-bounded access

The Effective from / Expires at fields make a membership temporary:

Effective fromExpires atResult
emptyemptyActive now, indefinitely
empty31 Dec 2026Active now, auto-revoked after 31 Dec 2026
1 Sep 2026emptyScheduled — activates on 1 Sep 2026
1 Sep 202628 Feb 2027Active only within that window
Example — a 6-month postdoc

Add Dr. Lee to schmidt-lab with Expires at = 30 Jun 2027. Lee gets access today; on 1 Jul 2027 the scheduler revokes the membership and re-projects — no manual cleanup, and it shows up on the Expiry dashboard (§8) beforehand.

Status values active (counts toward access), scheduled (future start), expired (window passed), revoked (ended manually). Only active memberships grant access.

Change dates or remove a member admin group manager

In the Members panel, Dates extends or shortens an active/scheduled membership; Remove ends it and withdraws the access from SciCat right away. Ended memberships cannot be revived — add the person again.

Administrators are safe SciCat's admin groups are reserved names that this app never manages, so it cannot remove anyone's administrative access.

View a person's groups admin group manager

On the Users page, search a user to see every group they belong to, with status and dates, plus their current SciCat access groups.

6. Projection to SciCat

Projection is how membership becomes real access. It runs automatically on every membership change and on a schedule, so you rarely trigger it by hand — but the controls are on each group's detail page.

ActionWhat it does
Project nowRecomputes effective access for the group's members and writes it to SciCat now.
ReconcileCompares intended vs actual access across users, reports any drift, and fixes it.
Your manual SciCat edits are preserved Projection only ever adds/removes the group names this app manages (and names of groups it deleted). Other strings (globalaccess, role strings, groups set elsewhere) are never touched.
Logins reset SciCat's groups — the app restores them SciCat rewrites a user's access groups each time they log in. The app notices within ~15 seconds and restores the managed groups (immediately when catorga loads the user's permissions). Changes you make here take effect in SciCat right away, without the user logging in again.
Example — recovering from drift

Someone edited a user's access groups directly in SciCat and removed a managed group by mistake. Click Reconcile: the drift is listed and corrected so SciCat matches the app's intended state again.

7. Resource grants

Open Resource Grants to attach a group to SciCat resources — datasets, origdatablocks, proposals or samples — individually or in bulk. (SciCat instruments and jobs have no group fields, so they cannot be granted.) Managers see only resources owned by their own groups.

Apply a group to resources admin group manager

  1. Pick a Resource type (e.g. dataset) and optionally Search or filter by Owner group.
  2. Tick the resources you want; selections are kept while you page with Next/Previous.
  3. Click Apply group (N).
  4. Choose the Group and a Mode:
    ModeEffect
    accessAdds the group to each resource's accessGroups (read access). Existing groups are kept.
    owner adminSets the resource's ownerGroup to this group. The previous owner is recorded and restored when the grant ends. A resource can have one owner grant at a time.
  5. (Optional) set a time window, then Apply.
Per-item results Bulk applies report success/failure per resource. If 2 of 50 fail (e.g. a deleted dataset), the other 48 still succeed and the 2 errors are listed — re-try just those.
Example — share a proposal's data

Filter datasets, select all 24 belonging to proposal 42, Apply group proposal-42 in access mode. Every member of that group can now read those datasets in SciCat.

Remove a grant admin group manager

Use the Applied grants tab (or the grants panel on a group's page) and click Remove. A grant only undoes what it did: if the group already had access (or ownership) before the grant, it stays. For an owner grant the previous owner is restored — unless ownership was changed in SciCat meanwhile, in which case it is left alone.

"removal pending" If SciCat refuses the change, the grant stays in effect, is marked removal pending with the error, and the scheduler retries every few minutes (or click Retry). Reconcile also re-adds access grants that were removed in SciCat by hand and reports owner changes made outside the app.

8. Expiry dashboard

Open Expiry for a forward-looking view of temporary access. Choose a window (7–90 days) at the top.

PanelShows
Expiring soonActive memberships whose Expires at falls inside the window.
Recently expiredMemberships the scheduler revoked within the window.
Expiring grantsActive resource grants about to lapse.
Nothing to click to enforce it Expiration happens on its own — the dashboard is for awareness, e.g. to extend a membership before it lapses (open the group and edit/re-add the member with a new date).

9. Ownership transfer (departures)

When someone leaves, what they personally own must not be orphaned. That means resources whose owner group is their personal group (their username) and resources whose contact fields (owner, owner/contact email, proposal contact) name them. Data owned by shared groups such as projects or the lab stays with its group. Transfer rules map a departing user to a successor.

Create a transfer rule admin

  1. Open Transfers → New rule.
  2. Give it a Name and optional filters: a specific user, a group they were a member of when leaving, and/or that group's category. Blank = applies to anyone.
  3. Choose the Successor type (user or group) and pick the Successor.
  4. Set Priority (lower = checked first) and, for a user successor, whether to also hand over the contact fields (owner, emails) that name the departing user.
  5. Save. Rules can be edited later.

Deactivate a departing user admin

  1. Go to Users, find the person.
  2. Click Deactivate & transfer and confirm. All their memberships end (removing that access in SciCat) and their personal resources are handed over.
  3. A summary reports how many resources were transferred, need manual handling, or failed.
Example — postdoc handover

Rule: was member of schmidt-lab, successor user Prof. Schmidt, with contact fields. When Dr. Lee leaves, click Deactivate & transfer: datasets owned by Lee's personal group move to Schmidt's, and where Lee is named as owner/contact, Schmidt is named instead. Datasets owned by schmidt-lab itself are untouched. Each change is in the history.

Never silently orphaned; safe to retry If no rule matches, nothing is changed and the resources are flagged pending_manual (warning banner on the Transfers page). Each departure is listed under Departures; after adding or fixing a rule, click Retry — completed transfers are never repeated, failed and pending ones are re-evaluated, and ones you fixed by hand show as resolved. Departures that hit SciCat errors are retried automatically. Deactivation does not block the person's login; disable the account in the university directory for that.
Expiry can trigger transfers too If a user's last membership lapses, the scheduler runs the same transfer logic automatically (rules are matched against the group that lapsed), attributed to the system actor in the audit log.

Transfer history admin

The lower table on the Transfers page lists every reassignment: when, from whom, the resource, what was changed, and the outcome (transferred / pending_manual / failed / resolved); hover the outcome for notes and errors.

10. Audit log admin

Open Audit for a chronological, filterable record of every change.

  • Filter by actor, entity type (group / membership / grant / projection / transfer / user) and a date range.
  • The Source badge distinguishes user actions from automated system actions (scheduler).
  • Click a row to see the before/after detail of that change.
Example — "who removed Alice from the team?"

Filter entity type = membership, actor = the suspected user (or leave blank), set the date range. The matching membership.revoke entry shows who did it and when, with the before/after.

TermMeaning

ProjectionComputing a user's effective access and writing it into their SciCat identity.
ReconcileDetecting and fixing differences (drift) between intended and actual SciCat state.

ownerGroupThe single group that owns a SciCat resource.

DriftA mismatch between what the app intends and what SciCat actually has.

Troubleshooting & FAQ

"A change I made in SciCat disappeared."

If you edited a managed group on a user directly in SciCat, the next projection/reconcile restores the app's intended value. Make membership changes here, not in SciCat.

"I can't create a group — name rejected."

The name is reserved, already exists, or matches a per-user group. Choose a distinct name (§4).

"Bulk apply shows some failures."

Those specific resources couldn't be patched (often deleted or renamed in SciCat). The rest succeeded; re-select the failed ones and retry.

"A deactivated user's resources say pending_manual."

No transfer rule matched. Create a rule (§9) and re-run the deactivation, or reassign those resources by hand in SciCat.

"Buttons to change things aren't showing."

You are signed in as a non-admin / non-manager. Read access works for everyone; ask an admin for the role you need (§3).

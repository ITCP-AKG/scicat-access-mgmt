SciCat Access Management — User Manual

The source of truth for access groups, membership, resource grants, expirations and ownership transfer across your SciCat instance.

Legend for who may perform an action: admin SciCat administrators   group manager a user listed as a manager of that group   any user any signed-in user (read-only)

1. What this app does

SciCat can store an access group on a user or a dataset, but it has no place to manage those groups — to say who belongs to a group, for how long, or what happens when someone leaves. This application fills that gap. It is the source of truth; it computes each person's effective access and writes it back into SciCat automatically.

You do this here……and the app does this to SciCat
Add Alice to group catalysis-teamWrites catalysis-team into Alice's UserIdentity.profile.accessGroups
Apply group proposal-42 to 30 datasetsAdds it to each dataset's accessGroups (or sets ownerGroup)
Give a postdoc access until 31 DecActivates and then automatically revokes access on that date
Deactivate a departing userReassigns their owned datasets to a successor and logs every move

2. Signing in (SSO)

Open the app and you are taken to the sign-in screen. Authentication is handled by SciCat, so you use the same institutional single sign-on (SSO) account you use for SciCat itself.

  1. Click Sign in — you are redirected to your institution's SSO login.
  2. Authenticate (username/password, 2FA, etc. as configured by your institution).
  3. You return to the app, already signed in. Your name appears top-right, with (admin) if you are a SciCat administrator.
New users First-time users who sign in via SSO are recognised automatically from their SciCat identity — there is no separate account to create here. What you can do depends on your role (next section).
Sessions Your session uses your SciCat token. Use Sign out (top-right) on shared machines. If actions start returning "unauthorized", your token has expired — sign in again.

3. Roles & permissions

RoleCan do
adminEverything: create/delete any group, manage any membership, apply/remove grants, run projection & reconcile, define transfer rules, deactivate users, and view the audit log.
group managerManage membership and grants for the groups they manage. Managers are listed on each group (the Managers field).
any userBrowse groups, members, a user's groups, the expiry dashboard and transfer history (read-only).
Why an action is greyed out or returns 403 Buttons that change data only appear for admins (and managers, where relevant). If you believe you should have access to a group, ask an admin to add you to that group's Managers list.

4. Groups

Open Groups from the left nav. This is the registry of every managed access group. Each group's name is the exact string written into SciCat.

Create a group admin

  1. Click New group.
  2. Enter a Name (e.g. catalysis-team-alpha), pick a Category, add an optional Description.
  3. Click Create. The group appears in the list.
Example

A new research group joins the lab. Create research-group category group schmidt-lab, description "Prof. Schmidt's surface catalysis group". You can now add members (§5) and grant it access to resources (§7).

Reserved & duplicate names are rejected Names that collide with SciCat's special groups (admin, globalaccess, all, ingestor, archivemanager, …), with an existing group, or with a per-user group are refused with an explanatory error. Pick a distinct, descriptive name.

Edit, retire or delete a group admin

Click a group row to open its detail page. From there you can edit the description/category/managers, retire it (keeps history, stops new use), or delete it.

Delete is guarded If a group still has active members, active resource grants, or is referenced by a transfer rule, deletion is blocked. Confirm the impact warning to cascade (members revoked, grants withdrawn, referencing rules removed) — or clean those up first.

5. Membership

Membership is who belongs to a group. Manage it from a group's detail page (Members panel), and review it per-person from the Users page.

Add a member admin group manager

  1. Open the group → Add member.
  2. Search the directory in the user picker and select the person.
  3. (Optional) set a time window — see below. Leave blank for indefinite access.
  4. Click Add. The change is projected to SciCat immediately.

Time-bounded access

The Effective from / Expires at fields make a membership temporary:

Effective fromExpires atResult
emptyemptyActive now, indefinitely
empty31 Dec 2026Active now, auto-revoked after 31 Dec 2026
1 Sep 2026emptyScheduled — activates on 1 Sep 2026
1 Sep 202628 Feb 2027Active only within that window
Example — a 6-month postdoc

Add Dr. Lee to schmidt-lab with Expires at = 30 Jun 2027. Lee gets access today; on 1 Jul 2027 the scheduler revokes the membership and re-projects — no manual cleanup, and it shows up on the Expiry dashboard (§8) beforehand.

Status values active (counts toward access), scheduled (future start), expired (window passed), revoked (ended manually). Only active memberships grant access.

Remove a member admin group manager

In the Members panel, click Remove on the row. Access is withdrawn from SciCat right away.

Last-admin safeguard You cannot remove the final member of a configured admin group — this prevents locking everyone out. Add another admin first.

View a person's groups any user

On the Users page, search a user to see every group they belong to, with status and dates, plus their current SciCat access groups.

6. Projection to SciCat

Projection is how membership becomes real access. It runs automatically on every membership change and on a schedule, so you rarely trigger it by hand — but the controls are on each group's detail page.

ActionWhat it does
Project nowRecomputes effective access for the group's members and writes it to SciCat now.
ReconcileCompares intended vs actual access across users, reports any drift, and fixes it.
Your manual SciCat edits are preserved Projection only ever adds/removes the group names this app manages. Intrinsic strings (a user's personal group, globalaccess, role strings, groups created directly in SciCat) are never touched.
Example — recovering from drift

Someone edited a user's access groups directly in SciCat and removed a managed group by mistake. Click Reconcile: the drift is listed and corrected so SciCat matches the app's intended state again.

7. Resource grants

Open Resource Grants to attach a group to SciCat resources — datasets, origdatablocks, proposals, samples, instruments or jobs — individually or in bulk.

Apply a group to resources admin group manager

  1. Pick a Resource type (e.g. dataset) and optionally Search to narrow the list.
  2. Tick the resources you want (the checkbox column; select many for a bulk apply).
  3. Click Apply group (N).
  4. Choose the Group and a Mode:
    ModeEffect
    accessAdds the group to each resource's accessGroups (read access). Existing groups are kept.
    ownerSets the resource's ownerGroup to this group. The previous owner is captured so it can be restored.
  5. (Optional) set a time window, then Apply.
Per-item results Bulk applies report success/failure per resource. If 2 of 50 fail (e.g. a deleted dataset), the other 48 still succeed and the 2 errors are listed — re-try just those.
Example — share a proposal's data

Filter datasets, select all 24 belonging to proposal 42, Apply group proposal-42 in access mode. Every member of that group can now read those datasets in SciCat.

Remove a grant admin group manager

Removing a grant withdraws the group from the resource in SciCat. For an owner grant, the previously-captured owner group is restored.

8. Expiry dashboard

Open Expiry for a forward-looking view of temporary access. Choose a window (7–90 days) at the top.

PanelShows
Expiring soonActive memberships whose Expires at falls inside the window.
Recently expiredMemberships the scheduler revoked within the window.
Expiring grantsActive resource grants about to lapse.
Nothing to click to enforce it Expiration happens on its own — the dashboard is for awareness, e.g. to extend a membership before it lapses (open the group and edit/re-add the member with a new date).

9. Ownership transfer (departures)

When someone leaves, their owned resources must not be orphaned. Transfer rules map a departing user to a successor; deactivating the user then reassigns their resources automatically.

Create a transfer rule admin

  1. Open Transfers → New rule.
  2. Give it a Name and optional Match filters (user ID, group, and/or category). Blank match = applies to anyone.
  3. Choose the Successor type (user or group) and the Successor.
  4. Set Priority (lower = checked first) and, for a user successor, optionally toggle Transfer owner/email to also reassign owner/ownerEmail.
  5. Create.

Deactivate a departing user admin

  1. Go to Users, find the person.
  2. Click Deactivate & transfer and confirm.
  3. A summary reports how many resources were transferred and how many need manual handling.
Example — postdoc handover

Rule: match userId = j.lee, successor group schmidt-lab. When Dr. Lee leaves, click Deactivate & transfer: every dataset Lee owned is reassigned to schmidt-lab, each move recorded in the history with previous → new owner.

Safe to re-run; never silently orphaned Transfers are idempotent — running a deactivation twice does not double-move anything. If no rule matches, the resources are flagged pending_manual (a warning banner on the Transfers page) instead of being left without an owner.
Expiry can trigger transfers too If a user's last access lapses by expiry, the scheduler runs the same transfer logic automatically, attributed to the system actor in the audit log.

Transfer history any user

The lower table on the Transfers page lists every reassignment: when, from whom, the resource, the new owner, and the outcome (transferred / pending_manual / failed).

10. Audit log admin

Open Audit for a chronological, filterable record of every change.

  • Filter by actor, entity type (group / membership / grant / projection / transfer / user) and a date range.
  • The Source badge distinguishes user actions from automated system actions (scheduler).
  • Click a row to see the before/after detail of that change.
Example — "who removed Alice from the team?"

Filter entity type = membership, actor = the suspected user (or leave blank), set the date range. The matching membership.revoke entry shows who did it and when, with the before/after.

Troubleshooting & FAQ

"A change I made in SciCat disappeared."

If you edited a managed group on a user directly in SciCat, the next projection/reconcile restores the app's intended value. Make membership changes here, not in SciCat.

"I can't create a group — name rejected."

The name is reserved, already exists, or matches a per-user group. Choose a distinct name (§4).

"Bulk apply shows some failures."

Those specific resources couldn't be patched (often deleted or renamed in SciCat). The rest succeeded; re-select the failed ones and retry.

"A deactivated user's resources say pending_manual."

No transfer rule matched. Create a rule (§9) and re-run the deactivation, or reassign those resources by hand in SciCat.

"Buttons to change things aren't showing."

You are signed in as a non-admin / non-manager. Read access works for everyone; ask an admin for the role you need (§3).
